# Large canonical Node worker

This is dormant preparation. Neither building the image nor rendering a chart authorizes a production rollout, schema apply, privilege grant or flag change.

Build `docker/large-read-worker.Dockerfile` with `SOURCE_REVISION` equal to the checked-out commit. It uses Bun 1.4.2 only to install and bundle, and Node 24.21.0 to execute. The bundle is produced by `scripts/build-large-read-worker.ts` with the same derived-schema plugin as the Lambda build, so the migration generation and verifier SQL are embedded and the runtime image contains neither `supabase/` nor `node_modules`. The separate services image does not contain this entry point. The image CMD is `node --max-old-space-size=49152 /app/large-read-main.mjs`; run it under the independently measured capacity envelope; no public ingress is needed. Disabled startup reads no credentials, opens no sockets and makes no database, S3 or network calls; it only loads the bundle (Node reads its own OpenSSL/resolver configuration) and writes one JSON status line to stdout.

Required environment when explicitly enabled:

- `SESSION_LARGE_READ_WORKER_ENABLED=1`; `SESSION_LARGE_READ_MAX_JOBS=1` by default, valid 1–10.
- `SESSION_PIPELINE_SECRET_JSON` from the existing secret contract (Supabase URL and ClickHouse client configuration), injected through a secret reference.
- `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, optional `AWS_SESSION_TOKEN`, from an approved credential reference. This runtime does not implement ambient federation exchange.
- `PIPELINE_RAW_S3_BUCKET`, `PIPELINE_KEY_PREFIX`, `PIPELINE_ORG_FROM_PREFIX=true`.
- Optional `PIPELINE_RAW_S3_SSE=AES256` or `aws:kms`; `PIPELINE_RAW_S3_KMS_KEY_ID` requires `aws:kms`.

No secret values belong in chart values, logs, source or proof artifacts. The runtime needs existing backend RPC execution, ClickHouse ingestion, current raw S3 Get and normalized/read-projection Put/Get, plus the applicable KMS permissions. It does not need Neon access, raw overwrite, object deletion or version access. Missing runtime identities and permissions remain an operator dependency; none are granted here.

The process advances a persistent 128-scope keyset cursor before consuming jobs, with at most 16 pages per invocation. The cursor rotates across the whole eligible catalog, so an interrupted reconcile does not repeatedly strand cohorts after the first page. Unknown or legacy zero counts use conservative large-worker routing (an activation blocker, see below). A source is not acknowledged on enqueue alone: the existing nonce-bound job must publish a current source epoch/fingerprint and complete under the same valid lease. Repeated scans coalesce unchanged jobs. A discovery page that raises (for example SQLSTATE 54000 from a scope over 10,000 pointers, or an ambiguous canonical source) rolls back as a whole, cursor included; the worker logs `large worker discovery failed` with the bounded code only, still claims already-queued jobs, stops rescanning for that invocation and exits non-zero (`discoveryFailures` in the status line). Until follow-up migration 20261105032000 isolates per-scope discovery failures, such a scope stalls discovery of every scope after it in cursor order. Five failed attempts poison a job (`failed`) for explicit repair; errors retain bounded codes only. A failed job is never claimed again, and because the event consumer skips search and replay for a delegated scope, that scope stays unindexed and unpublished until its source changes (a new source epoch/fingerprint re-queues the job). With the handoff on, the consumer reads the job state once per delegated scope and logs `large scope job will not be processed` (warn, `state`, `attempt`) for a failed or missing job, and `large scope delegated` (info, `state`) otherwise. A route refused on capacity (SQLSTATE 54000) is logged as `large scope handoff refused` and falls through to the normal search and replay stages. A route refused because the canonical source is ambiguous (SQLSTATE 55000 with capture's exact message `replay capture: ambiguous canonical source`) is deterministic too: it is logged the same way with `reason` `large_handoff_ambiguous_source` and `error_code` 55000, plus the scope ids, and falls through to search. Other route errors (55000 `durable handoff unavailable` or `source epoch missing`, 22023, connection errors) fail the batch and are retried.

The worker renews every 30 seconds against a 120-second lease. Wall-clock expiry is checked after source capture and after potentially blocked publication; losing expiry rolls back provisional publication. A 30-minute process timer and SIGTERM/SIGINT prevent a new publication after shutdown is requested. Abrupt process loss leaves the lease reclaimable. Every output object is verified before the final source CAS. A shared 64 MiB hydrated-row bound refuses generations the reader cannot serve; no row is silently truncated.

Measured synthetic capacity, not live parity: 1,550,924,671 raw union bytes; 901,653 unique ClickHouse rows; 21,254 verified output objects totaling 5,482,859,417 bytes; 600.972 seconds. Peak RSS 8,672,305,152 bytes and cgroup peak 12,389,949,440 bytes in a 64 GiB / 8 CPU container. Four actual workerd HTTP proofs preserve exact windows/cursors, tenant/revision fences and full 2,360,000-character content with 10,000 tools. The standard profile refuses the same source before raw reads. These results do not establish live backfill completeness, production latency, every admitted extreme, or a production identity/resource plan.

Activation blockers for `SESSION_LARGE_READ_HANDOFF_ENABLED` (keep it unset/0 until all are resolved; none can be fixed without SQL, and follow-up migration 20261105032000 is reserved for them):

- Discovery isolation: one scope whose enqueue raises (54000 over 10,000 pointers, 55000 ambiguous source) rolls back the whole `discover_session_large_reads` page and its cursor, so every later scope in cursor order is never discovered. The worker now logs and keeps claiming, but discovery stays stalled until 20261105032000 isolates per-scope failures.
- 0/NULL-count routing: `route_session_large_read` (and discovery) treat any pointer whose `raw_bytes` or `event_count` is 0 or NULL as large. `event_count` is optional in the manifest, so ordinary small scopes can be delegated, and with the worker off or a job `failed` they get no search index. 20261105032000 must route on measured size only.
- Failed jobs: a `failed` job leaves its scope unindexed until a source change (logged, not repaired). Activation needs an explicit repair path or alerting on that warning.
- Claim isolation: `claim_session_large_read` captures each queued job (`capture_session_replay_pages`) with no per-job error handling. A job queued under 10,000 pointers whose scope then grows past them (54000) or becomes ambiguous (55000) raises on every claim, stays `queued` with 0 attempts and its early `available_at`, and so wedges every claim for every tenant until it is repaired by hand; the worker's run rejects each time. 20261105032000 must isolate claim failures per job alongside discovery isolation and the 0/NULL-count no-delegate routing.
- Ambiguous-source refusal: with the handoff on, a route that raises 55000 ambiguous canonical source is logged as `large scope handoff refused` (`large_handoff_ambiguous_source`) and the scope falls through to search; nothing is queued. If replay pages are also enabled, the replay stage still treats the same 55000 as a batch failure, so that scope reaches the DLQ unpublished. The ambiguity itself needs data repair; activation needs alerting on that warning.
- Failure causes: every processing failure is recorded as the single reason `large_processing_failed` (`retry_session_large_read`), so a poisoned job does not say whether it hit a source bound, S3, ClickHouse or a lease loss. Activation needs bounded per-cause codes or an equivalent operator diagnostic.
- While the worker is off, every delegated scope stays `queued` and unindexed; do not enable the handoff before the worker runs.

Before activation: independent review of this runtime/discovery composition, final image revision/digest, chart-owned default-off execution plan, exact least-privilege operator plan, applied SQL/ACL, full current publication, all search on ClickHouse, all selected desktop reads on Supabase/S3, erasure parity, fresh gates and rollback. No 48-hour canary wait is required; the accepted post-switch observation still applies.
