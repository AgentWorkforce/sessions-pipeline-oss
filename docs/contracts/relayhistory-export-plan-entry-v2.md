# Contract: plan entry v2, a backfill epoch on a live manifest (O4)

Status: **draft proposal, code only.** v1 ([`relayhistory-export-plan-entry-v1.md`](relayhistory-export-plan-entry-v1.md)) is unchanged and still covers cold exports. v2 covers the straddling case: a session that already has a live manifest when its pre-T0 records are exported. Its records land as one sealed `backfill` epoch appended to that manifest. This follows #42's owner fence and #46's backfill rules.

Test vectors: [`relayhistory-export-plan-entry-v2.vectors.json`](relayhistory-export-plan-entry-v2.vectors.json). They were generated by `packages/pipeline/src/lib/pipeline/migration-assertions.ts` (byte-identical in relayhistory-cloud) and cross-checked by an independent Python implementation. The v2 vectors reuse v1's grant and two manifests unchanged, and add one backfill.

## Why a new version

A v1 entry signs a session's **whole** chunk list. A backfill appends chunks to a live stream whose length, epoch and object version keep changing until the moment of the append. The plan cannot know them.

v2 splits the identity into two parts:

- **The entry** (stored in the plan, part of the plan digest) lists only the backfill's own chunks. Their positions are relative, as #46's `BackfillEpoch` lays them out: offsets contiguous from 0, no `seq`, no epoch number.
- **The base** is the live manifest the backfill appends to. The issuer signs it at mint time from the mint request. The ingest then checks it against storage.

## The v2 plan entry (stored under the plan's `backfills`)

| field                                                  | value                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `v`                                                    | integer `2`                                                                                                                                                                                                                                                                                                                                          |
| `kind`                                                 | `"backfill"`                                                                                                                                                                                                                                                                                                                                         |
| `grant_id`, `org_id`, `workspace_id`, `source_user_id` | as in v1 (canonical ids, no `relay_` prefix)                                                                                                                                                                                                                                                                                                         |
| `key`                                                  | the live session's v1 manifest key, without any deployment prefix                                                                                                                                                                                                                                                                                    |
| `session`                                              | `{machine_id, harness, session_id, started_at}` of the live session                                                                                                                                                                                                                                                                                  |
| `format`                                               | `"ndjson"` (a backfill epoch needs an ndjson stream, #46)                                                                                                                                                                                                                                                                                            |
| `chunks`                                               | `[{start_offset, bytes, sha256, records}]`: `sha256` is the SHA-256 of the chunk's **source** bytes; `start_offset` runs contiguously from 0; 1 to 4096 chunks; **`records` is mandatory** (#46's optional `records` must be filled in before planning; a manifest chunk without it is refused at commit); safe-integer bounds as in the issuer spec |
| `backfill_sha256`                                      | #46's `backfillDigest`: the manifest v1 content hash chain over `chunks` with every `epoch` set to 0                                                                                                                                                                                                                                                 |
| `raw_bytes`                                            | the sum of `chunks[].bytes`, which equals the end offset                                                                                                                                                                                                                                                                                             |

- **`entry_sha256`** = lowercase hex `SHA-256(canonical(entry))`, with the same canonical JSON as v1.

## The plan digest with backfills

- **With at least one backfill:** `plan_digest` = `SHA-256(canonical({v: 2, grant_id, exported_at, manifests, backfills}))`, with both lists sorted by key.
- **With no backfills:** the plan digest is exactly v1's, so every v1 grant and vector is unchanged.
- **Who checks it:** the issuer stores the plan and checks this digest, as for v1.

## The signed v2 upload identity (`meta.upload` with `v: 2`)

```
{ v: 2, kind: "backfill",
  grant_id, plan_digest, key, org_id, workspace_id, source_user_id,
  session: {machine_id, harness, session_id, started_at},
  backfill_sha256, entry_sha256,
  base: { revision, version, owner, writer, chunk_count, epoch, content_sha256 } }
```

The `base` fields describe the stored live manifest at mint time:

| `base` field     | meaning                                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `revision`       | its `revision` (1 or more); the backfill commits `revision + 1`                                                |
| `version`        | its object version id, or else its ETag exactly as the store returns it; the commit's compare-and-swap version |
| `owner`          | its `raw.owner`, the live owner, which must not start with `migration:` and is unchanged by the append         |
| `writer`         | its `writer.delivery_instance_id`, unchanged                                                                   |
| `chunk_count`    | its `raw.chunk_count`; the backfill epoch's `first_seq`                                                        |
| `epoch`          | its `raw.epoch`; the backfill epoch is `epoch + 1`                                                             |
| `content_sha256` | its `raw.content_sha256`                                                                                       |

## Issuer, base read and route matrix

These are normative in [`relayhistory-export-plan-entry-v2-issuer.md`](relayhistory-export-plan-entry-v2-issuer.md), the **spec of record on main at `f67f741`** (96BullSessions #86, which passed contract review). It has its own vectors. In summary:

- **Plan with backfills:**
  - The issuer stores the plan, and checks `records` (mandatory), contiguous offsets and safe-integer bounds on every backfill chunk.
  - It derives `backfill_sha256` and `raw_bytes` itself.
  - With absent or empty `backfills`, the plan is the exact v1 plan.
- **The base comes from the pre-mint base read:**
  1. The courier mints a **base-read capability**: its own token class `migration_base_read`, scope `rth:migration_base_read`, audience `<origin>/v1/pipeline/manifests/base`, TTL of 30 s or less, `meta.read`, a `jti` starting `mbr_`, and its own replay table.
  2. It calls `GET /v1/pipeline/manifests/base?key=<signed unprefixed key>`.
  3. The ingest takes one storage snapshot and validates it. Then, in one transaction, it consumes the capability and appends an audit row (`result = base_read`, and the key's digest instead of the key). Only then does it return exactly the 7 base fields.
  4. The courier mints the v2 commit assertion with `upload: {key, base}`, copying that base verbatim.
- **The commit compares the exact returned base with storage,** including the `previousVersion` compare-and-swap. A base that changed is refused: 403, or 409 on the version.
- **Route matrix:**
  - a base-read capability reaches only `/base`;
  - every upload or ordinary token is refused on `/base` (403 `migration_token_class_forbidden`);
  - matching is exact (method case, one trailing slash, no other normalization).
- **The base read is default-off** (`RELAYHISTORY_ACCEPT_MIGRATION_BASE_READ`). When off, `/base` gives 404, and a base-read capability fails verification.

## What the ingest checks

- **All requests:** the same as v1, meaning the dedicated default-off verifier, the three routes, the signed pair, the grant list, canonical ids, the 5 s skew and single use.
- **v2 is admitted only where the commit can verify it.** A deployment must set `migrationBackfill` (96BullSessions' ingest does). Elsewhere a v2 token gets **403 `migration_backfill_unsupported`**; for example the relayhistory-cloud Worker, which has no #42 fence.
- **Chunks (`POST /v1/pipeline/chunks`):**
  - The request carries the canonical v2 entry in front of the bytes (`X-Relay-Migration-Plan-Entry-Length`), and the entry must hash to the signed `entry_sha256`.
  - Its key, tenancy, session and `backfill_sha256` are the signed ones.
  - The chunk's position comes from the **signed base**: `seq = base.chunk_count + i`, `epoch = base.epoch + 1`. Its offset, size and the SHA-256 of the actual bytes must equal the entry's chunk `i`.
- **Status:** a v2 commit token reads only its own session's status (its version). The base comes from the base read, not from status.
- **Commit (`POST /v1/pipeline/manifests`).** Every condition below must hold, else 403 `migration_upload_forbidden`:
  - The **stored** manifest is exactly the signed base: same `revision`, version, `raw.owner`, writer, `chunk_count` (equal to the chunk list length), `raw.epoch` and `content_sha256`, and it has no backfill epoch yet. `previousVersion` must be the stored version, else 409 `revision_conflict`.
  - The **incoming** manifest is the base plus exactly one epoch: `revision = base.revision + 1`, the same owner and writer, `raw.format = ndjson`, and `raw.epoch = base.epoch + 1`.
  - The base's chunks and epochs are unchanged.
  - The one new epoch is `{epoch: base.epoch + 1, reason: "backfill", first_seq: base.chunk_count, opened_by: "migration:<grant_id>"}`.
  - The added chunks are numbered `seq = base.chunk_count + i` in that epoch.
  - The hash chain is recomputed.
  - The added chunks, re-derived into a v2 entry with the signed tenancy, the key and the live session, hash to the signed `entry_sha256`, and also give the signed `backfill_sha256`.
  - #42's owner and backfill fence still runs, as does the provenance check: export marker `grant_id`, `plan_digest` and `source_user_id`, plus `96bulls.user_id`, equal to the signed values.
  - The read-back copy must be the appended manifest.
- **Work key:** `upload.key + "@" + upload.entry_sha256 + "@r" + (base.revision + 1)`. The base revision is signed, so a rebuild on a newer base after a lost compare-and-swap race is new work. The consumer (`objectLandedWorkKey`) accepts it only through the job's `payload.migration = {key, entry_sha256, base_revision}`.

## Lost races

- If a live write commits between the mint and the commit, the stored manifest is no longer the signed base, and the commit is refused (403, or 409 on the version).
- The courier then rereads the base, mints a fresh assertion with the new base, re-seals its chunks at their new `seq` (#46: keys embed `seq`), and commits again.
- `backfill_sha256` and `entry_sha256` do not change, because they are position-independent. Only `base` and the work key's `@r` suffix do.
- **Lost commit response.** If the stored object is already byte-identical to the commit, a retry under a fresh assertion with the same base returns the original success and work key. The stored manifest is then the appended one, so the stored-base comparison cannot run. Instead the append is checked against the signed base, and the historical `previousVersion` must be present and resolve exactly to the signed `base.version`, else 409 `revision_conflict`. Nothing is consumed or written on a refusal.

## Not covered

- #46's `resumed` epoch for the live client after the backfill. That is #46's client-side rule, and the ingest's v2 check stops at the append.
- A cold export followed by a live handover (#52).
